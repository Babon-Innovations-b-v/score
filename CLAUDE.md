# CLAUDE.md

SCORE: an environment synthesis framework that turns what a creator locks into a complete, owned, editable environment (coding agents and open models in cloud batches, checks before every paid step), and its paper. Public repository, MIT. Owner: `@JoeyKardolus`.

## Persona

Read [`.claude/soul.md`](.claude/soul.md) for voice, hard rules, and working rhythm. Match it.

## Workflow protocol — every conversation in this repo

**On the first user message in any conversation, invoke the [`grill`](.claude/skills/grill/) skill before generating any response.** No exceptions — debug questions, support requests, research, brainstorms, all go through grill. Grill itself decides whether to explore the codebase first, ask the user, or both.

A conversation in this repo is a **task**. The flow is fixed: grill → to-prd → code → [`close`](.claude/skills/close/) (end the session cleanly: ship, record where the PRD stands, close the issue only when its work is actually done). Two branches: grill's dump check sends a **brain dump**, a message that is a page of thinking rather than a task, to [`brain-dump`](.claude/skills/brain-dump/); and grill's wayfinder check sends efforts too big and fogged for one session to [`wayfinder`](.claude/skills/wayfinder/) (the effort is a PRD; its foggy pieces become investigation sub-issues, one resolved per session, until the route is clear). Otherwise grill always routes to [`to-prd`](.claude/skills/to-prd/), which synthesises the aligned plan as a PRD-style issue with no re-interview, and carves a sub-issue under the PRD when a task is independently grabbable or going ready-for-agent. First message contains `#N` or a GitHub issue URL → resume mode inside `to-prd` (re-align against the existing issue body plus the bible, amend if it drifted, then code). Long autonomous chains run under YOLO mode (`claude --dangerously-skip-permissions`); the audit-* skills and a local test run before pushing catch what permission prompts would have. Term definitions: [`CONTEXT.md`](CONTEXT.md).

**Brain dump, the first branch.** It fires whenever a message arrives as several open questions at once, visionary thinking, or a pasted conversation rather than a task. Like every skill here it is checked into the repo, so it is the same workflow for whoever is working in it. [`brain-dump`](.claude/skills/brain-dump/) sorts it into claims, questions, decisions and vision, sweeps and refutes the first two in one workflow, lands each result in its own home (a new word in `CONTEXT.md` first, a trade-off on its issue or as a proposed ADR, the thinking in the chapter it belongs to, an invariant in its bible chapter), then hands the route to `wayfinder` and creates the issues. Also `/brain-dump` by hand.

Four mechanism types make this loop work — **skills** (methodology, `/<name>`), **overlays** (per-directory `CLAUDE.md`, auto-load on file-touch), **hooks** (harness-event automation via `.claude/settings.json`), **GitHub issues** (durable backlog). One job each; mixing them creates unpredictable harness behaviour.

## Agent tools

One tool is wired in for every session and agent here, pinned (`.claude/settings.json`):

- **ponytail** (lean-code rules, v5.1.0, `vendor/ponytail`), injected at session start and into coding sub-agents. Where it differs from the house rules, the house rules win: one function, one purpose still means split; no `shortcut:` comments.

**Output: summaries, not dumps.** Every output an agent reads stays in its context and is paid for again on every later turn, so long output goes to a file and the agent reads only the part it needs. A tool here prints one summary line (counts, pass or fail, the paths it wrote) and writes the detail to a file; `--verbose` gives the full output where a tool has it. The `output_cap.py` hook (PostToolUse on Bash) does the same for any command: an output over 6,000 characters is saved whole to `/tmp/score-output/<session>/<call>.txt`, and the agent sees its first and last lines, its error and warning lines (or, for JSON, its keys and array lengths) and that file's path. Nothing is lost: read the file with Read (offset, limit), `grep` or `sed -n`. Reads you narrow yourself (`sed -n`, `head`, `tail`, `grep -c`, `wc`) and a `cat` of a rules file you must read whole (a `CLAUDE.md` overlay, `SKILL.md`, `soul.md`, `CONTEXT.md`) are left alone, and a command prefixed with `SCORE_FULL_OUTPUT=1` keeps its whole output. Read a large file in ranges rather than with `cat`. A failing command's output cannot be replaced by a hook; Claude Code shows about 10,000 characters of it, so send a long failing run to a file yourself (`cmd > /tmp/x.log 2>&1; tail -n 40 /tmp/x.log`).

**Never wait in the foreground** (owner, 2026-10-09). An agent's turn that comes more than 5 minutes after its previous one re-writes its whole context to the prompt cache; on 2026-10-09 that was about half of all agent spend, mostly after sleep and poll loops, cloud runs, Blender and game runs and test gates that blocked in the foreground. So start anything that takes minutes with the Bash tool's `run_in_background` and go on with other work, or end your turn and let the completion notice wake you. The cloud Blender tools take `--detach` (`blender_cloud.py`, `tools/usd/settle.py`, `tools/review/page.py`), and `tools/cloud/detached.py -- <command>` does the same for any command, a test gate included: progress goes to a log and one result line (status, log, outputs) comes at the end, so there is nothing to poll and no log to read whole. To wait for a condition, use the Monitor tool. `.claude/hooks/wait_guard.py` blocks foreground sleeps over a minute, poll loops and foreground cloud Blender runs. Every session here keeps its prompt cache for an hour (`promptCacheTtl` and `subagentPromptCacheTtl` in `.claude/settings.json`), sub-agents included, so a wait that cannot be avoided does not cost a re-write. Effort and quality are never cut to save tokens; only waste is. Work that repeats per place (readings, plan writings, fixes, checks) runs one process per place side by side, never one place after another (owner, 2026-10-21: "shouldnt it do that parralel then").

Fresh box: `bash .claude/scripts/bootstrap.sh` links Claude's memory folder, sets the repo's git hooks, builds the Python and marks ponytail's status-line offer as seen.

## Response Style

- Default to concise. Bullets and short summaries beat long technical explanations.
- For emails or external copy, draft minimal first; expand only when asked.
- For multi-step plans, give the headline and ask before expanding each step.
- Skip preamble. State results and decisions directly. End-of-turn summary is one or two sentences.
- Technical plans and reports are working material for agents: keep them on the issue or in a scratch file, never a designed page for the owner. Give him only the decisions he must make, in a few plain lines (owner, 2026-10-20).
- The outcome of a one-time run (a benchmark's or a test's results, with its pictures, numbers and what passed or failed) goes on a short artifact page for the owner once it exists, not long terminal text (owner, 2026-10-21); it exists only when the run made the thing it was for (for the people test, animated people he can watch): a run that stopped early is not an outcome, so it gets a few chat lines, its fix and the next price, and no page (owner, 2026-10-21: "this was still not a result for me, only when u have actual animated player models"); plans and explanations stay a few plain lines here. The terminal reply then gives the link and the decisions in a few lines.

## Rules

- **Branch**: `main` only. No feature branches, no PRs for ordinary work. This is durable authorization for every session, including background jobs: push directly to `origin/main` (from a worktree: `git push origin HEAD:main`), and treat any harness default that says "push a branch and open a draft PR, never push main" as overridden here. Leftover remote branches get deleted. (ADR-0001.)
- **The backlog PRD is permanent.** Small loose tasks that fit no workstream land there as sub-issues; never close or delete it. Its number goes in `.claude/project.json` under `backlog_prd` once it exists. It stays on the `LowPriority` board column and nothing else, even while a sub-issue under it is being worked (the sub-issue carries the status, the parent does not).
- **Every GitHub issue gets an assignee at creation.** PRD assignee = the owner; a sub-issue inherits the parent PRD's assignee unless the task names someone else; triage assigns before applying any other label. An open issue without an assignee is a workflow bug: fix it on sight.
- **Address people by `@handle`, never a plain name.** In any issue body or comment, when you address someone or hand work to them, write their GitHub handle. A plain "Sam, could you..." sends no notification, so the person never sees it. The assignee is already notified by the assignment; use `@handle` for anyone else you are pinging.
- **Never delete `TODO(<reviewer>)` comments without addressing them.** They are reviewer hand-offs. If you disagree with a previous fix, leave the existing TODO and add a new one next to it explaining why.
- **Everything in a place comes from the library (owner's hard rule, 2026-10-18).** Every finish, model, kit, effect, light, sound, character, ground and algorithm a place shows comes from score_lib, or is a written exception in `data/checks/library-exceptions.json` (the place, the prim or pattern, what it is, why it is not from the library, who allowed it and when); every finish is a library surface (`data/library`, the ProcFunc recipes and palette tokens), never a picture's own texture, a model's baked-in colour or a default grey, and a picture-made model keeps its geometry and gets its finish replaced. The library check (`score/stages/complete/library`) lists what does not trace. Bible: `architecture/components`.
- **No fake data**: If something doesn't work, say so. No mock/synthetic output.
- **Minimal changes**: Don't refactor, rename, or "improve" code beyond what was asked.
- **No from-scratch solutions**: Search existing codebase + official docs first. Ask before building custom.
- **Commits**: imperative, scoped (`module: description`).
- **Test files follow the module standard and run in under 2 minutes (hard rule, owner 2026-10-21).** One test file a module, named `test_<invariant>.py`, its docstring naming the break that turns each test red; small fixtures, never the real store or home. `make tests` enforces it: its guard (`tools/test_rule/check.py`, owner 2026-10-26) fails on a second test file in a module, a misnamed file or a missing break, and it fails a file over its budget. `docs/bible.md#workflowmodule-standard`.
- **Verify after refactor**: After deleting >20% of a module, run the full import chain + one smoke test before committing.
- **A new `.md` file needs the owner's go-ahead (hard rule).** Ask before creating a markdown file anywhere in this repo, and take no for an answer. Every `.md` here is living: someone reads it, it has one clear purpose, and it is kept current, so the count stays minimal. What would have been a new file goes into an existing one, into a `docs/bible.md` chapter, or as a comment on the issue it belongs to; a generated page renders to a path outside the repo. **This includes ADRs**: a decision goes on the issue where it was made, and into its `docs/bible.md` chapter when it is load-bearing; an ADR is a one-line proposal ("want this as an ADR?") and gets written only after a yes. Editing an existing `.md`, ADRs included, is free. **Per-area `CLAUDE.md` overlays are the one standing exception**: a new code directory gets its overlay without asking, because the overlay is the mechanism that loads the directory's rules and a directory without one is a gap, not a document. `.claude/hooks/md_guard.py` blocks the creation routes (Write, shell redirect, `tee`, `touch`, `cp`). When he says yes in a session, the agent adds the path with his words and the time to `.claude/hooks/md_allowed.json` and writes the file; the guard lets listed paths through, and the git-ignored `.claude/memory/` too (owner, 2026-10-21: "fix that rule its stupid"). `vendor/` is exempt: third-party code comes with its own docs, kept as released. (ADR-0003.)
- **One function, one purpose**: Functions doing >1 thing must be split. If the docstring needs "and" between concerns, split it.
- **No single-letter variable names** in production code. Comprehensions and lambda arguments are exempt because the binding's lifetime is one line.
- **Agents: one clear role, then a handoff and a close (hard rule).** New work goes to a fresh agent with its own role brief, never a second job mid-run; coordinating sessions start inside this repository. `docs/bible.md#workflowloop`.
- **Delete dead code**: stubs, unused exports, archived "we might need it" leftovers all go. Apply the deletion test before adding new code.
- **No loose files outside the carve-out**: every directory contains only subdirectories plus an explicit carve-out list (framework-required files only: `__init__.py`, `conftest.py`, `pyproject.toml`, `uv.lock`, `package.json`, `package-lock.json`, `tsconfig.json`, `vite.config.ts`, `build.gradle`, `build.gradle.kts`, `settings.gradle`, `settings.gradle.kts`, `gradle.properties`, `gradlew`, `gradlew.bat`, `Makefile`, `Dockerfile`, `docker-compose.yml`, `README.md`, `CLAUDE.md`, `CONTEXT.md`, `LICENSE`, `docs/bible.md`). Anything else loose must move into a named subdir. `vendor/` (vendored third-party tools, kept as released) is exempt wholesale. ADR-0002. Carve-out is append-only by ADR amendment, and `docs/adr/tools/check_index.py` checks this list against ADR-0002's copy so the two cannot drift.

## Deployment

Nothing is deployed. A push to `main` publishes the source, the paper's PDF and its arXiv tree; nothing runs from it. No GitHub Actions.

**Public from the first commit.** Nothing from babon or Movalytics (business files, data, people, clients), no secrets, keys or cloud account and project ids, ever: not in code, docs, the paper or its comments.

**Claude's memory stays private.** `.claude/memory/` is git-ignored: this repository is public and memory is private working notes, so it is never committed or pushed. Anything a later session must know goes into the bible, `CONTEXT.md` or an issue.

**Parallel agents (owner, 2026-10-21: agents were taking an hour each re-testing and waiting on each other).** One agent per area at a time (the concept code, the plan code, the cockpit pages, the reading each have one owner; new work on an owned area waits or goes to that agent). An agent runs only the tests of the modules it touched, pushes, and stops; it never re-runs whole suites after a rebase, never waits on the hosted rebuild or a sync, and never releases: the coordinating session releases once for a group of landed changes, then checks the live pages. A whole-suite run happens once on main after a group lands.

## Autonomy boundaries

- Don't continue into adjacent work after the requested task is done. Stop and wait.
- When a background monitor reports repeated failures, propose stopping or investigating; don't passively echo "awaiting direction".
- Never ship unverified claims (measured numbers, benchmark figures, compatibility assertions).
- Costs of a few cents (a bucket download, a small read) need no approval; say them in the report after (owner, 2026-10-19). Paid runs, machines, model calls and basket checkouts still wait for his yes.
- **Benchmarks up to €20 a batch may be approved in a Claude Code session** (owner, 2026-10-20, answered to the session's question "Confirm this standing rule: in a Claude Code session, I may ask you to approve a benchmark batch of at most €20 ... It covers benchmarks only; anything else and anything over €20 still needs your cockpit click" with "Yes, set this rule"). The session asks him with its question tool; his yes is recorded (his answer, time, amount, purpose) as the grant. A grant holds its euros until they are spent (owner, 2026-10-22, his yes to "a grant shouldn't be used up by a run that fails after spending cents. It should hold the €20 until it's spent."): every benchmark batch run under it draws its real spend, finished or failed; the money guards clear a run only while its high estimate plus 10% fits in the balance left; the grant is done when the balance runs out, never because a run ended or time passed (owner, 2026-10-23: "remove the expirey date, it wasted a bunch of time now"). Everything else, and anything over €20, still needs his click in the creator cockpit.
- **An agent may stop a batch itself** (owner, 2026-10-25, on being asked to press Stop this batch for a run holding 13 idle machines: "this is also something u should just do urself"): through the agents' door, `stop-batch <reason>` stops the live runs, pools and parked machines with no free-only latch, the reason recorded. Stopping only ends spending; starting or allowing paid work stays as above.
- **A Buy may be approved in a Claude Code session** (owner, 2026-10-25, "this is stupid, change the rules, i should be able to confirm my buy with u aswell, u just click the button", then "Yes, set the rule and buy" to the session's question "Set this standing rule: in a Claude Code session you may approve a Buy in chat. I ask you the exact price and stop line, record your answer, the time, the amount and the basket, and then press Buy for you through the cloud machine. The stop line works exactly as when you click. It is never more than you approved, and a changed basket or a higher price needs a new yes."). The session first reads the agents' door's `batch-money` and asks with its question tool in batch totals (owner, 2026-10-26: "the stop should be a total of the batch, not per try, i have no clue now"): "Batch N: EUR X spent so far (the money guard's measure: its runs EUR R, other spend meanwhile EUR O); this try likely EUR L, high EUR H, its share EUR S (high plus 10%); Batch N's total stop EUR T?", T at least X plus in flight plus S; his yes is recorded (his answer, the question, the time, the batch total, this try's high, the basket) by `buy-yes --batch-total T H ...` and the agent launches that checkout through the agents' door, with the same money guards and checks as his click, the stop line the batch's start plus T. A try under an approved batch total launches whenever the batch has room left in it (a retry under the same yes too, `buy <yes id>`), even when its high plus 10% needs more: the stop line stays at the total and the guard stops the try there, so it may stop before every step is made, and the door and the Buy page say so (owner, 2026-10-27: "why did u do that before, and not just stop when u got to the limit, like ur supposed to"). A Buy is never launched with nothing left of the approved batch total, its stop line never above that total, never on another basket, and never on a higher price without a new yes.
- **A spend approval is for the whole batch, not one try** (owner, 2026-10-26: "i feel like those budget asks should become per batch tho, not per try, i keep oking stops but i have no idea how far the previours even got filled"). His Buy click or his yes in chat sets the batch's one budget across all its tries: the batch's spend so far (every try, warm pool time included) plus what he approved, raised only when that is more. Every try draws from it: the stop line is the batch's start plus its budget, so the money guards stop at the budget less what earlier tries spent. A retry that fits what is left needs no new ask (in a session: `buy <the same yes id>` again through the agents' door); only a try that would go over asks again. The monitor, the Buy page and the door's `batch-money` show one spent figure, the money guard's own measure since the batch's first line (`checkout/watched.batch_money`), its runs' own share beside it: "Batch N: EUR spent of EUR budget, EUR left" (`score/dashboard/checkout/flow.batch_budget`).
- **Design edits the owner asks for in a session may be made by the agent** (owner, 2026-10-21): renaming, merging, adding or removing child scenes, moving and resizing things on a plan, editing an inventory row, when he asks for it in chat; each is recorded as his edit with his words quoted and the time, like a benchmark grant. Concept and film locks, accepts, rejects, waivers and spend are his: his click, or his recorded yes in a session (below; a Buy above).
- **The owner may make every owner-only decision in chat** (owner, 2026-10-27: "i hate the rule that i cant make discisions in chat aswell"). An accept, a reject, a waiver, a concept lock and a film lock may each be his answer in a Claude Code session, applied exactly like his click. The session asks with its question tool naming exactly what it applies to (the node and output, the check, the place and draw, the film as its editor shows it); his yes is recorded (his answer, the question, the time, the decision and its target as it stood) by `decide-yes <decision> <target> ...` through the agents' door (for a run on his PC, `tools/cloud/this_pc.py decide-yes ...` against that run's home), and `decide <yes id>` applies it once through the cockpit's own request code (`score/dashboard/sync/chat_decisions.py`, `sync/applying.apply`) with every check of his click, refused when its target changed since the question (another output accepted, another lock, the script edited), like a changed basket refuses a Buy. Never by writing store files: `.claude/hooks/accept_guard.py` still blocks an agent's own accept, reject, waive or lock and lets through only `decide` with a recorded yes's id. The cockpit stays (owner, 2026-10-27: "the cockpit is also just there for us to make us accountable for making the framework usable for other people"): it is the surface other creators use, kept complete and working so the framework stays usable by people who are not in a session, and a decision made in chat is the same record as his click, shown on the cockpit as his, so the two never diverge. A run he gives his go in chat counts as a bought batch for the in-batch accept below (owner, 2026-10-27, his "sure" to: "let a free run you started accept passing results on its own, like a bought batch, so the run doesn't stop for clicks"): `decide-yes go <environment> ...` records his go, and the run carries its id (`SCORE_OWNERS_GO`, set by `this_pc.py env1 --go <id>` or the door's `run ... --go <id>`, checked by `score.review.web.owners_go`). - **A failing result is remade without asking when the remake is free** (owner, 2026-10-28, after being asked to confirm free remakes of failing objects: "dont understand why i had to confirm that? the goal was getting to the film"). A result that fails its own checks is rejected and made again on a free machine (this PC's card, Claude), once, with the same checks; only a remake that costs money, or a second failure, comes to him, priced. - **Inside a bought batch a passing worse result is accepted** (owner, 2026-10-27, his "yes" to: "Inside a bought batch, a result that passes every check is accepted automatically, even when a measure is worse than before; the drop is written down for you to review after the batch, never as a wait. - **Scene inventory readings and plan writing are allowed without asking** (owner, 2026-10-21): reading a locked concept into its scene inventory (the Gemini rows and the SAM 3 boxes) and writing its plan (one Gemini call) run on their own after a lock, with no separate yes; every call's cost is recorded and the running total stays visible in the creator cockpit.

## Verification

- On "u sure?" or any audit/consistency check, recount from scratch — don't reuse prior assertions.
- For research/citation tasks, check current sources before drafting; do not answer from memory.
- Failures propagate. A silent `except: pass` around a write is an anti-pattern; don't add one.
