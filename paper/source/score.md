# Introduction

Interactive 3D environments are the raw material of games, film and embodied AI [@yang2024holodeck], and building one is expensive: every object is modelled, surfaced, placed, given collision, lit and given sound in one style, and the environment stays editable. Generative models promise to take over much of this, but in GDC's 2026 survey 52 percent of game workers thought generative AI was hurting the industry [@gdc2026survey]; a tool for building environments has to leave the result in the creator's hands.

World models generate an environment as frames [@bruce2024genie; @genie3] that no engine can open. 3D environment generators [@wang2025worldgen; @hyworld2] produce geometry, but mostly as one fused asset, from which separate objects are recovered after the fact [@hu2026worldact; @niu2026worldsculpt]. Both work in one shot, so a creator cannot find or change the step behind a fault. Procedural systems [@raistrick2023infinigen; @raistrick2024indoors] and coding agents that write scenes as programs [@hu2024scenecraft; @li2026rcwm; @guo2026worldclaw; @yin2026autoue] keep the environment explicit, but rebuild a scene that already exists or draw their objects from a fixed library, and such agents judge their own geometry unreliably [@li2026lego]. Open vision foundation models [@oquab2023dinov2] now read shapes [@li2026pixal3d], masks [@carion2025sam3], depth [@wang2025moge2] and parts [@lin2025partcrafter] out of pictures, and a coding agent can connect them as tools; none of them provides one style across objects that different models made, which the field names as an open problem [@wu2026production; @yang2026flowscene].

Recent agents write Blender programs and check them against a target: from one image, in stages of geometry, materials, composition and light [@he2026thinking]; from text or video, as worlds for physical reasoning [@wang2026codeasworlds]; and with motion added [@zhang2026code2worlds; @liu2026simworlds]. Benchmarks find that their procedural models often float or come apart [@gao2026codebench3d], and that on dynamic scenes rebuilt from video the best model scores 0.91 on static scenes but 0.67 on dynamic ones; mesh quality does not track fidelity, and VLM judges agree with people in 89.3 percent of comparisons but near chance between close models [@shen2026codebench4d]. SCORE builds static environments in explicit, gated stages and treats motion as its own checked layer, which this gap between static and dynamic scenes supports.

Studios build environments in stages, each with an output a person can check; SCORE keeps these stages and automates them. Its environments are meant to be **complete**: every object, surface, light and sound exists wherever the viewer looks. They are **owned**: every model in the framework allows commercial use of its output, so the creator stays the author, holding the full commercial rights. They are meant to be **responsive**: every object has real collision, mass and material. And they can be any kind of **environment**, from a house on a plot of ground to a system of worlds. To our knowledge, no other openly available environment generation work joins vision foundation models into engine-ready scenes that are built from reference pictures, steered by a person's choices at each step, and made only with models that allow commercial use of their output.

We contribute **the SCORE framework**, a design step the creator owns and stages as nodes of one runner that keys, judges and accepts every output over one canonical scene (Section 2); **measured gates** for every layer of a place and a completion gate over them (Section 3); and **evidence from a first environment**, which separates what its runs prove from what is built but has not run and what is missing (Section 4).

# The framework

An environment is a table of stages; environment 1's has 149 rows, 89 of them one for each person's look, dress or take. A **node** is one stage for one place (`assembly@hangar`) or for the environment, and one runner makes, judges and accepts every node. The creator works in the creator cockpit, one signed-in web page: there he designs each place (Section 2.2), buys paid work as batches and reviews what the runner reports. From an approved design everything runs without a further yes.

## Keys, gates and accepts

**Keys.** A node is made only when its key has no finish record. The key hashes the stage and place, a code version, the contracts of its output and inputs, its parameters, a seed derived from the environment's, the pinned model images, every environment file it reads and the accepted output of every node it reads. The code version hashes every source file the stage imports, leaving out the runner and the renting code, which change what a run costs, not what it makes. A fault fixed in one stage moves only its key and those after it. Outputs are kept by content hash, never overwritten.

**Gates and accepts.** Each gate answers pass, fail or unknown, with measures and a reason; missing evidence is unknown, and unknown blocks like fail. The runner accepts an output by itself when every gate passed and it is no worse than the one accepted before: no answer dropped, no measure moved the wrong way by a step a viewer could see, no gate missing. Later nodes read only accepted outputs. The creator keeps four actions, buttons in the cockpit applied on his own PC: reject an accepted output (it moves back to the one before, and every node that read it is stale), accept a worse one with a reason, waive one gate for one key, and override the runner for one paid run. When the creator accepts a worse output, that accept records what was allowed, and a later output no worse than the one taken is accepted with that accept named. None is needed for a run; a barrier keeps agents from them (a store that refuses the creator's records from an agent's process, and a hook).

**Batches.** Paid work is bought as a batch. Before it starts, the runner gives one estimate and one ETA from measured unit costs (Section 3.7); the creator's yes to that estimate is the only spend decision, and the batch's stop is its own high estimate plus 10 percent. Inside a batch every paid job runs once, with no retry; its checks only sort each output into a success or a named failure, and a failure becomes a batch gap that the line carries to the completion gate instead of stopping. Spending more on a gap is a new batch and a new yes. A paid node is cleared only when every gate on its inputs passed, the month's books are known from the providers' bills, and its batch's stop has room for its forecast; everything that rents a machine or calls a paid model refuses without that clearance, and buying again more than EUR 5 of accepted outputs needs a written reason. Each node's review page is built from the store alone, and the creator reviews a place in a 3D viewer on the store's copy of its accepted assembly.

**The creator steers: the ship.** Figure 1 shows the creator's control on one piece of environment 1, the ship, in its first run. The creator's picks were found pictures of a shuttle, a one-deck cutaway, a cockpit and crew quarters; we do not show them. From them an agent planned the bridge alone (v1, a 4.6 by 4.6 m room of 27 pieces). The creator corrected the plan in words: a smaller cockpit, the rooms environment 1 needs, a long flat wedge rather than a rocket, a nose less pointed, and an outline measured from drawings rather than shaped from words. Each correction made a new plan, and the creator accepted the seventh. Every plan is ours and cost nothing; the two drawings the outline was traced from cost EUR 0.28 and are not shown. The ship's shape follows found artwork the creator chose to use: shuttle concept by PAUL (zana), found online.

## From concept to scene

**The design.** Before any paid batch the creator decides each place's design: its concept and its plan. He first locks an environment concept, in a short interview with Gemini 3.1 Pro [@gemini31pro] in the cockpit: its style, his reference pictures, its first places with the places each may hold, and its **setting**, what everything stands on and in at the scale he sets: a plot of ground with a gravity and a sun path, one world, or a system of bodies that move one another, a real body taking its values from a cited table and an invented one given by its radius, mass, orbit and spin. Each thing in the setting takes the form its scale calls for: a body near enough to matter moves under the physics, a far source of light is a light, and what is too far to move is a backdrop. An environment plan, written by the plan writer below, places each top place's site on the setting's ground at true size and works out each site's sky at its scene time. Concepts are drawn layer by layer on a concept review page, each draw one Nano Banana Pro [@nanobananapro] call that the creator's click pays for, where he marks areas and asks for a new draw. Every new draw is sent a **blockout** first: a grey model built in code from its parent's plan at real sizes and rendered free from the fixed concept view, so the draw keeps its layout and proportions and adds the look. A place within another is drawn only once its holder is picked and planned, on a crop of the holder's concept and its own shell inside the holder's, so inside places fit the shell they stand in.

**Inventory and plan.** The creator's pick is the approval. It starts the scene inventory reading: Gemini 3.1 Pro lists every object of the picked concept as a row with its kind, count, anchor and size in metres, judged against the place's outline, and SAM 3 [@carion2025sam3] boxes each row on the concept; a row without metres, or a disagreement between the two, is a named gap. One more Gemini 3.1 Pro call writes the plan in metres, element by element, as environment 1's hand-written plans were: outline, walls, openings with their swing, levels, stairs, roofs, terrain heights, each item's shape and a section. The SAM 3 boxes only order the items, since boxes from a perspective painting laid flat put objects in the wrong place. Free checks follow, each failure a gap said where it is: every row placed as often as it counts, inside the outline, no two floor items in each other, every door and standing spot reached on foot, and the inside places tiling the shell. On the plan review page the creator moves, resizes and corrects, and his edits redo what follows. Readings and plan writings run without a yes under the creator's standing allowance, their cost shown in the cockpit. Only a place with a design gets the rows of a batch.

**Shapes first.** The route is one loop, the same at every scale. A place starts as its big shape, the outside shell, with a concept, a plan and a rough model: the concept goes through picture to model whole, and the rough model gives the plan its proportions. The shell's plan is then split into the shapes of the places inside it (rooms, corridors, holds), each sized inside the shell. Once those shapes are fixed, every place's concept, rough model, close-ups and finishes are made in parallel, since from then on each is a matter of proportions inside a fixed shape; zooming into an inside place repeats the same steps. This is the creator's order of 19 October 2026. The runner has its two rows: `rough-model` puts a place's concept through Pixal3D whole after its plan, and `shell-split`, free, cuts an outside shell's plan into its inside places' shapes, gated on `tiled`, `reached` and `bounded`, which each inside place's plan reads. Neither has run on environment 1: no rough model has been made, and no plan of it has a split yet.

**Plan and scene record.** Nothing is made or placed that is not an inventory row. The plan stage is gated on `mapped` (every element a row, a door or a written drop; every door says where it leads). The scene record is written from the plan, inventory, made ground and sky, gated on `game-free` (the record cites nothing from the game the environment came from), `plan-matched` (the shell within 5 cm of the plan), `openings` (every doorway onto a floor, no view into nothing) and `seed-matched` (every old entry matched or dropped with a reason). The `game-free` gate sees cited numbers only. In environment 1's first run a coding agent wrote the inventories and plans, and in 18 of its places the data still took positions from the source game (Section 4).

**The canonical scene.** Every place is one OpenUSD stage [@openusd]; each object, one per real-world object, carries its kind, transform, collision and each part's library surface. Its layers lie in a fixed order: a slot for the creator's edit layer on top, then people, sound, light, motion, effects, crops, machines, settle, ground and the generated base. The edit layer exists only as that slot, an empty layer the exporter makes once and never writes again; a test on a two-box place shows an edit there surviving a regenerated base, but the runner's assembly does not yet carry a creator's edit from one assembly to the next. Each place is assembled once, from every layer's accepted output; its `layers` gate answers unknown while a needed layer has none, and an old output never stands in.

A close-up that fails the shape check's measured half (a plain border, one object filling the frame, the row's proportions) is a batch gap, so Pixal3D is never paid for it. Only an object whose checks fail is built by a code builder a coding agent writes, reversing the earlier parts check (the creator's choice, 12 October 2026). On 13 of the hub's objects both orders end the same (Table 1, Figure 2), but generation first draws a close-up of every object. Every close-up of eight thin and flat objects failed the shape check, so code builds carry them. # Stages and their gates

## Surfaces: the finish route

Everything a place shows comes from the creator's library, score_lib, or is a written exception: every model, kit, finish, effect, light, sound, character, ground and algorithm (the creator's rule of 18 October 2026). Models give shape only, picture-made and code-built alike, so one style holds across them: a picture-made model keeps its geometry and its finish is replaced, never kept as the picture's own texture, its baked-in colour or a default grey. Every part takes one surface from a shared library of rule-based surfaces, written as ProcFunc functions [@raistrick2026procfunc] on Infinigen's shaders [@raistrick2023infinigen], coloured from the place's palette and worn only where wear has a cause (Appendix D).

The finish route gives each model its finishes (the creator's choice of 20 October 2026). Free renders of the raw model cover every face from as many angles as a coverage check needs, and each view is split into colour regions of the model's own texture. One Gemini 3.1 Pro answer a model, a place's models in one batch, lists its finishes, each matched first to a library surface with its settings (palette token, roughness, metal, seed), and labels each region of each view. Before anything is baked, a free check compares each region with its label's surface and makes a model whose colours lie more than ΔE 32 off a gap; the labels then vote across views into one finish a face, and a face no label reaches or whose views disagree is a gap too. Each part is painted from its library surface and baked in one paid job, and one batch recheck against the close-up sorts each model into a pass or the named gap "no library surface fits". This route replaced the finish-map route of environment 1's first run, in which Nano Banana Pro drew the close-up again with one flat colour per finish, up to three times, and SegviGen [@li2026segvigen] split the mesh along that map; that route gave every piece its own rust and stains until the parts were painted from the library (Appendix A). The finish route has run its free views on two places; its paid steps have not run.

The bake is checked against the close-up. A finish's surface must lie within ΔE 32 of its colour there, else a nearer surface of its family is taken or a new one is proposed to the creator, and the part fails by name. From the greenhouse's water tank, which the creator found baked as three near greys and tipped, came two checks: a bake fails when it darkens a finish the close-up shows lighter, or turns all surfaces into one grey; and short legs are stretched onto one level plane, a foot over 3 cm off the floor failing. The bake's finish borders follow the model's real edges, as the cut-down copy it bakes onto is shaded smooth except at folds of 60 degrees or more.

A written exception names the place, the object, what it is, why it is not from the library, who allowed it and when; only the creator allows one, and one without a reason or an owner refuses the whole file. A free library check traces every material, model, emitter, light, sound source and character of a place's accepted assembly to a library entry, by content hash or a recorded origin, and the cockpit shows what does not trace as the place's problems. It is not a gate of the completion gate, since wiring it in would move the keys of paid rows; instead the library rows at the end of every line, which hand each accepted output to the library, fail when an output is covered by no entry or written exception, so nothing reaches the library untraced. Each new entry then gets a preview clip, rendered in the batch with the films' renderer.

## Resting

Loose objects are dropped onto the made ground in a physics simulation; one that would turn more than 15 degrees or drift more than 30 cm is a resting fault of the layout and keeps its laid pose. The settle stage lays where each object comes to rest as a layer (held objects snapped onto their holders, a stack onto one support, an object that would rest worse kept as laid), gated on `rested` and `resting` (no fault that appears with the layer and not without it).

## Light

Lamp strengths are measured, never copied from the source game. The light layer places live lamps from the scene record, with the sky and its bodies. One paid render per place gives every lamp its own Cycles light group on the place's views; because light adds up, the look at any strengths is mixed from these passes without rendering again, and a free sweep chooses the scale that brings the place's brightness within 1.5 times its concept's, halving any lamp that turns what it lights white. Outdoors the suns are swept after the lamps. A lamp whose fixture stops 90 percent of its rays moves out of it, and one behind a clear lens stands just outside, as Cycles passes no light through a glowing lens.

## Motion, effects and sound

**Motion.** Each moving thing (a path, a hinge, a spin, a rail, a turn, a climb) has its kind's speed range cited from real machines, gated on `clear` (no moving thing within 3 cm of a still thing or another moving thing, read every quarter second), `speeds`, `loops`, `grounded` and `covered` (every still prim of a moving kind says why). **Effects** are emitters measured against real footage (photographs of lift-offs, rover films of Martian dust devils), gated on `attached`, `footage`, `light` (the flame lights the pad at least twice as brightly as the place's lamps) and `outside` (no open-sky particle inside a room). **Sound:** every source a place names (room tones, objects, motions, each surface's steps) gets the environment's picked file or one MOSS-SoundEffect [@moss2026] take of its brief, gated on `sources`, `level`, `likeness` (CLAP [@wu2022clap] score at least 0.30, the tenth percentile of the environment's picks; a take under it is a gap) and `no freesound`.

## Completion

A place is complete when its gate passes on its final assembly: every row made or dropped with a reason, nothing unmade, no placeholder or resting fault, the creator's picks shown, every layer and shown place present, nothing cited from the source game. **Accepted gaps.** A fault the creator decides to ship with is written down as an accepted gap: who decided, when, why, the objects and their measured faults. It moves only those objects' faults from the gate where they arise to the completion gate, which fails each gap by name with the numbers: a place whose accepted gaps are its only fail is complete apart from accepted gaps, every gap listed with who decided it; any other fault leaves it not complete, and the gate is never loosened. A batch gap moves the same way, the creator's yes to the batch being its decision, and is listed with the batch run that made it. A hook stops an agent claiming a place is done while its gate fails: agents judging their own scenes agree with a measured geometry score only 45.8 percent of the time [@li2026lego].

# Check details

- **Room checks** cast rays to find light leaking out through walls and roof, find pieces in front of a real opening and roof and wall fittings more than 3 cm off their surface or turned more than 5 degrees from it, and count pieces, triangles and lamps against the room's budget.
- **Door check:** every door must stand in a wall or partition that fully separates its two sides, tested by walking a grid from one side to the other.
- **Model check:** every model must have walls at least 3 mm thick. A generated box fails if one of its sides tilts more than 2 degrees or is warped. Making a generated model solid stops if its bounding box grows more than 3 percent.
- **Likeness gate:** a made model's outline from eight sides must overlap its close-up's by at least 0.50, a least set on the hub's twelve accepted generated models with a margin of 0.05, and its DINOv2 [@oquab2023dinov2] similarity must reach a least set the same way; without that calibration the gate answers unknown.
- **Finish maps (the first run's route):** a close-up's map passes when its outline overlaps the close-up's by at least 0.85 and it uses every listed finish; a part whose second finish holds 20 percent of its voted area mixes finishes and fails.
- **Bake check:** each baked part within ΔE 20 (CIE76) of its surface's colour, worn and dirtied as far as its place's wear and dirt, and within ΔE 32 of its close-up's; lightness order fails when the close-up shows one surface more than 10 L\* lighter and the bake makes it more than 3 L\* darker; one look fails when no two near-neutral surfaces bake far enough apart for a viewer to tell at the place's view distance, while the close-up shows them more than ΔE 24 apart. What a viewer tells is measured, not set: Stone, Szafir and Setlur measured the CIELAB difference half of their viewers see between two colours s degrees wide, per axis ND(50, s) = C + K/s, with (C, K) = (5.08, 0.75) for L\*, (5.34, 1.54) for a\* and (5.35, 2.87) for b\* on sizes 1/3 to 6 degrees [@stone2014size]; two surfaces are told apart when their difference, each axis over its ND, is 1 or more. A surface's size is its model's middle size times the root of its area share, seen from the place's nearest view. This replaced a fixed ΔE 12, which failed the wreck's access cover on a 9.3 L\* step between its steel and its scorched white that its owner sees (11.3 degrees from the nearest view; half of viewers see 5.2 L\* at that size); <!-- ND(50) constants: Stone et al. 2014, Table 3; sizes: score/stages/surfaces/bake_check.py seen_degrees on data/kit/wreck.json and data/scene/wreck.json; the cover's bake: its surfaces-check record, test in score/stages/surfaces/surfaces_test.py --> a quadrant of a standing model's base more than 3 cm off the floor fails. Glass, screens, lamps and print are judged by their own colour and left out of the order.
- **Settling and resting check:** an object that would turn more than 15 degrees or drift more than 30 cm when dropped keeps its laid pose and is marked as not resting; small debris, with no side over 1.4 m, may turn freely and drift up to 1 m. Hung objects are exempt by their inventory anchor, and fixed objects are not judged for tipping. The triage fails a foot off its support and an up axis leaning more than 3 degrees.
- **Light:** the place's median brightness within 1.5 times its concept's and every view within 2.5 times; a lamp is blown when over 20 percent of the pixels where it gives at least half the light are white, and unlit when it gives less than 0.001 percent of every view's light.
- **Motion:** no moving thing within 3 cm of a still thing or another moving thing, read every 0.25 s; rounds join within 1 mm; speeds within each kind's cited range.
- **Sound:** CLAP score against the brief at least 0.30, the tenth percentile of 55 of the environment's picks; a take no more than 0.5 s longer than its brief.
- **People:** the shell gate passes a look when 99 percent of its soft points lie within 5 cm of the fitted body; the worst point and its joint are recorded. A clip is usable when no frame tucks more than 5 mm, no hard part stretches past 1.2 times its bind length, cloth crosses cloth no more than in the earlier body's same clip, and no part's edges pass through cloth deeper than 3 mm more often than at the bind. A far-only look is judged on its joins, likeness and the far body's triangles (at most 1,220); the near outfit's triangles and shell offset are recorded, not gating. The A-pose outline is judged against the finished Pixal3D take the build starts from; the take's own loss against the raw model is recorded apart. A crowd copy stands only where it fills under a tenth of every view's height.
- **Worse than accepted:** a measure counts as worse only when it moves the wrong way by at least its tolerance, the smallest change a viewer could see: one more fault for a count; 0.02 of full scale for lightness on 0 to 1 (a halo, fill, beam or haze wash), and 5 of 255 levels for a colour gap, the step a viewer notices between two pictures; 0.05 for a brightness ratio; one percent of the picture for a share of it; a twentieth of the Earth's lit disc; 5 mm for a length. A score no viewer reads directly, such as a likeness score, is worse by any move. Tolerances decide only whether an output waits for the creator; a check that fails still fails.
- **The creator's accept carried forward:** when the creator accepts a worse output, that accept records what was allowed, each measure's value before and after. A later output that passes every gate and is no worse than the output taken, within the tolerances, is accepted by the runner with that accept named; a move beyond it still waits for the creator.
- **What the creator acts on:** the creator rejects, accepts or waives only an output already seen on its review page. This is the creator's rule; the commands do not yet check that the page was opened.
- **People seen by the cameras (experimental):** a clip's crossings of body through cloth are counted only where a camera that will show the person can see them: the place's views at the person's cast spot, and a close front and three-quarter view. Crossings no camera sees are recorded, not counted against the clip. So far this is a measure on the stored bodies (Section 3.5); the per-clip gate does not use it yet.
- **Completion gate:** the requirements given in Section 3.6, each with its result tied to a fingerprint of the stage's files and inputs; a result made on another stage counts as unknown. The placeholder check judges every mesh a code builder draws, and only the shell builders pass unnamed.

**People results in detail (experimental, Section 3.5).** The body gates are joins, outline, likeness, triangles and shell. Nev's and Sefa's boot tuck bands lie 9 to 11 mm outside the trouser leg at the bind pose, in every clip before any motion. Scored on drawn surfaces only, no clip of any look is usable: skin seams open and settled cloth crosses itself beyond the bind. Bound as one closed mesh, the player's limbs sink into chest and hips, 87 to 563 crossing points visible from the places' cameras and close views per clip, the armpit surface stretching between arm and chest. Where hair or cloth meets the head or hand skin the two sides are weighted differently and open as the joints move (cloth seams never open); openings over 10 cm on three looks are not yet confirmed by a render. # The surface library

The surface library holds families of variants, among them painted, steel, aluminium, rubber, plastic, cable, fabric, composite, glass, screen, light, print, wood, ground, foil, water, skin and hair. After the hub's second round it held 71 variants made from 14 ProcFunc recipes; it now holds 369 variants in 26 families made from 22 recipes. Each variant is a recipe with settings, takes its colours only from the palette, and is baked into base-colour, metal-roughness and normal maps at a texture density that depends on how close a viewer can get. Wear has three levels and comes from causes: edges, and kicks within 32 cm of the floor that a piece stands on. A surface the finish-map route proposes enters an append-only registry and joins the library only when the creator accepts it.

# With and without the agent tools

The tools that check an agent's work were tested on three places of environment 1: a room (the workshop, 814 objects), an outdoor place (the street, 1,198 objects) and a dense room (the hangar, 1,657 objects). They are the completion gate (Section 3.6); a triage of the resting check, which judges each object by what holds it up, read from its inventory row, and keeps only real faults [@tam2025sceneeval; @xia2026sage]; a pick lock, which refuses an export that would show anything but the model the creator picked for a row; and a render-and-compare, which lists the objects least like their close-ups by DINOv2 similarity [@oquab2023dinov2]. In both arms, the same agent (Claude Opus 5.5 in Claude Code, headless) started from the same exported stage and inventory and was asked to make the place as complete as it could in about 50 minutes, through its layout data only; one arm had the framework from before these tools. Each arm ran once, so Table E1 shows what happened, not an average.

No agent claimed a place was complete, so the gate's hook never had to refuse a claim. No row carries an owner's pick, so the pick lock was not tested.
