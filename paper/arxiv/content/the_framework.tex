\section{The framework}\label{the-framework}

An environment is stored as a single OpenUSD record. Each scene is one stage, a composed OpenUSD scene, that sits within its parent scene and holds its child scenes, each referenced at the room that the parent's plan, a dimensioned drawing in metres, assigns to it, so that opening a top scene opens everything below it. Each scene's layers are stacked in a fixed order of precedence, from a slot reserved for the creator's own edit layer at the top, through people, sound, light, motion, effects, crops, machines, physics, settle and ground, down to the base layer laid out from the locked plan. Each object corresponds to one real-world object and carries its kind, transform, collider and, for each of its parts, a surface from the library. The environment's physical setting is decided in its environment concept (EC), the top-level design the creator locks, as a plot of ground with its gravity and the path of its sun, as a single world, or as a system of bodies that move one another by gravitation. A real celestial body takes its values from a cited table, and an invented one is specified by its radius, mass, orbit and spin. The physics layer writes a scene's rigid bodies, masses, joints and the gravity of the body it stands on in OpenUSD's physics schema, so that any reader of that schema obtains the same scene.

The creator works in the creator cockpit, a single authenticated web page in which he locks the design, purchases paid computation and reviews what the framework reports. The work on an environment is represented as a table of stages derived from its designs, and the table for environment 1 has 261 rows. A node is one stage applied to one scene (written \texttt{assembly@hangar} for the assembly stage of the hangar scene) or to the environment as a whole, and a single runner produces, evaluates and accepts every node. Once the creator has approved a design, it runs without further approval.

\textbf{Keys.} A node is computed only when its key has no completion record, as in a content-addressed build system. The key is a hash over the stage and scene, the version of its code, its contracts, parameters and random seed, the pinned container images of its models, every file it reads and the accepted output of every node it reads. The code version covers only code that can shape the output. Code that decides where and how a job runs changes what a run costs but never what it produces, and is therefore excluded from every key. An edit or a fixed fault changes only its own node's key and the keys of the nodes downstream of it, so only those steps run again. Outputs are stored under their content hash and never overwritten.

\textbf{Gates and accepts.} Each gate is an automated acceptance test that returns pass, fail or unknown, together with its measurements and a reason. Missing evidence counts as unknown, and unknown blocks acceptance just as fail does. The runner accepts an output automatically when every gate has passed and the output is no worse than the last accepted one, and downstream nodes read only accepted outputs. Four actions are reserved for the creator. He may reject an accepted output, which marks every node that read it as stale, accept a worse output with a stated reason, waive one gate for one key, and override the runner for one paid run. Coding agents are prevented from taking these actions by a store that refuses such records when they come from an agent's process, and by a hook in the agent's harness.

\textbf{Batches.} Paid computation is purchased as a batch, a production run with a single cost estimate. The creator's approval sets the batch's budget across all of its attempts, and spending guards stop the batch when that budget is reached. Within a batch every paid job runs once, and a failed output becomes a batch gap, which the completion gate lists. Every paid stage is priced from a unit cost measured on the cloud billing ledgers. A stage that has not yet been measured in a run has no price, and its estimate is shown separately as a guess.
